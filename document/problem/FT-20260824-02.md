# FT-20260824-02: 수직 G1에서 횡이동과 끊기는 듯한 움직임

- 상태: OPEN
- 분류: ROBOT
- 누가: 오른팔 leader/follower smooth teleoperation 운용자
- 언제: 2026-08-24 05:03 KST, feedback-OFF G1 두 번째 반복
- 어디서: PC `leader_teleop_node`, `/right_dsr_controller/task_space_command`
- 무엇을: 운용자는 leader를 위·아래로 움직였지만 follower가 횡방향으로도 조금씩
  움직이며 끊기는 것처럼 보였다고 보고했다.
- 왜: 횡이동은 follower에서 새로 생기지 않고 leader raw FK부터 존재한다. FAST
  중력보상이 leader 자세를 옆으로 밀었을 가능성이 있지만 비교 실험 전에는 원인으로
  확정하지 않는다. 끊김 체감도 command, controller 또는 loop timing 중 어느 경로인지
  아직 확정하지 않았다.
- 어떻게: Smooth ON, feedback OFF로 FAST에 진입했다. 앞쪽의 빠른 오동작을 제외하고
  FAST 상대시간 약 `45 s`부터 G1을 다시 수행했다.

## 원인 분석

확인된 사실:

- `right_base_link`는 `base_link`에 대해 x축으로 약 `135 deg` 회전되어 있어 command
  frame의 y/z 동시 변화 자체가 world 횡이동을 뜻하지는 않는다. frame 변환 후에도
  실제 lateral component `14.67~18.55 mm`는 남는다.
- raw, intent/command, follower FK가 같은 횡방향으로 움직여 smoother나 follower
  controller가 독립적으로 횡이동을 만든 증거는 없다.
- command의 `3 Hz` 이상 RMS는 `0.062 mm`, follower FK는 `0.047 mm`로 고주파
  oscillation은 작다. 체감한 끊김을 이 값만으로 설명할 수 없다.
- 마지막 정지에도 leader raw 횡 drift가 먼저 발생하고 command/follower가 따라갔다.

미확정 가설:

- FAST 중력보상 joint torque가 leader를 횡방향으로 천천히 이동시킨다.
- operator의 Cartesian 경로가 leader 기구학에서 순수 world 수직이 아니었다.
- `23~33 ms` control-loop gap 또는 저속 leader 입력의 반복 가감속이 끊김 체감에
  기여했다.

## Leader-only 재현 결과

- 503,795개 전 행에서 `follower_command_publish_enabled=0`이었다.
- FAST는 `23.138 s`, `38.918 s` 두 구간이었다. 두 번째 FAST에서 follower 관절 범위는
  최대 `0.034 deg`, 시작-종료 변화는 최대 `0.026 deg`로 follower는 정지했다.
- 두 번째 FAST의 leader raw TCP world 범위는 `x/y/z=31.28/40.17/59.05 mm`, leader
  관절 범위는 `9.84/17.84/12.48/11.95/4.04/8.09 deg`였다.
- 두 번째 FAST 중 workspace `z=200 mm` 상한에 `13.346~25.533 s`, 약 `12.187 s`
  머물렀다. 이 구간은 수직 입력을 더 줘도 기록된 z가 증가하지 않아 정상 G1 판정에서
  제외한다.
- 두 번째 FAST loop gap `>10 ms`는 3회, 최대 `22.996 ms`로 반복적인 지그재그를
  timing gap만으로 설명할 근거는 없다.
- 중력보상 torque 범위는 joint 1/2에서 최대 `0.566/0.694 Nm`였고 damping torque
  절댓값 최대는 `0.009 Nm`였다. 현재 끊김을 damping이 주도했다는 근거는 약하다.
- leader URDF의 오른팔 moving-link 질량 합은 glove 제외 `0.7645 kg`이며
  `leader_right_link_1` 질량과 관성이 모두 0이다. 좌우 link-1 mesh의 정점·크기는
  동일하고 CAD export에서 왼쪽 대응값은 질량 `0.12 kg`, COM
  `[0,0,0.012353] m`이므로 오른쪽 inertial 누락은 모델 오류로 확인했다. 다만 이 COM은
  joint-1 축 위에 있어 왼쪽 값을 오른쪽에 복사한 Pinocchio 계산에서도 모든 자세의
  6축 중력토크 변화는 `0 Nm`였다. 따라서 수정 대상이지만 이번 지그재그의 직접 원인은
  아니다.
- FAST 진입 시 scale은 `[2.5,3.0,2.5,1.5,2.5,1.0]`에서 시작하지만 기존 코드가
  목표를 전 축 `1.0`으로 설정해 약 10초 뒤 모두 `1.0`에 수렴했다. 실제 수직 동작이
  시작된 FAST 약 11초에는 유효 gravity gain이
  `[0.25,0.25,0.45,0.10,0.30,0.10]`만 남았다. 운전자가 FAST에서 arm이 무겁다고
  느낀 것과 일치한다.
- 운전자 관찰: follower가 정지한 상태에서 leader가 내려갈 때 좌우 대각선을 번갈아
  움직이고 올라갈 때도 같은 지그재그와 끊김이 재현됐다.

따라서 follower controller와 follower command 경로는 이번 leader 물리 움직임의
원인에서 제외한다. 현재 우선순위는 FAST 중력보상 scale 부족, 실제 질량/무게중심과
URDF inertial 불일치, 관절 정지마찰/걸림 순서다.

## 조치

- G1/G2/G3 추가 반복과 parameter 승인을 중단했다.
- gravity/damping parameter는 변경하지 않았다.
- `follower_command_publish_enabled=false`일 때 raw/intent 계산과 CSV 기록은 유지하고
  공통 publish 지점에서 follower `PoseStamped`만 차단하는 leader-only 진단 모드를
  추가했다. 기본값은 기존 동작과 같은 `true`다.
- 진단 절차는
  [`teleoperation_stabilization_runbook.md` 9.2절](../stabilization_teleoperation/teleoperation_stabilization_runbook.md#92-follower-command-차단-leader-only-진단)에
  고정했다.
- leader-only gate를 포함한 현재 package build 성공.
- leader-only 재현 후 추가 stress와 gravity parameter 임의 변경을 중단했다.
  FAST의 joint별 보상량은 기존 `grav_gain`으로 조정하며, FAST scale은 전 축
  `1.0`을 유지한다. CURRENT/SLOW/PAUSE의 강한 보상에만
  `grav_sync_scale_per_joint`를 사용하는 기존 설계를 유지한다.
- 외부 leader URDF 두 파일의 link-1 inertial 수정은 물리 모델 변경 승인 전까지
  적용하지 않았다.
