# FT-20261110-01: 오른손 관절 피드백의 비정상적으로 큰 값

- 상태: CLOSED
- 분류: ROBOT
- 누가: 오른손 hand controller와 `/joint_states`의 `joint_state_broadcaster`
- 언제: 2026-11-10 KST, 세 모델 비교 실험의 박스 파지 준비 중
- 어디서: PC에서 조회한 `/joint_states`, `/dynamic_joint_states`,
  `/hand_joint_controller/joint_state_command`와 `/controller_manager`
- 무엇을: 오른손 15개 관절 position이 약 `6.99e8~1.85e9`로 읽혔다.
  파지 프리셋의 목표값은 약 `0~0.77 rad`다.
- 왜: 운용자는 SBC에 오른손만 연결했다고 확인했지만, 실행 설정은 양손을
  포함하고 오른손 slave를 `5~9`로 지정했다. 실제 응답은 왼손으로 지정한
  `0~4`에서 읽히므로 물리 손과 논리 이름의 배정이 맞지 않는다.
  비정상적으로 큰 관절값의 내부 생성 원인이나 Manus 문제와의 관계는 미확정이다.
- 어떻게: 이름으로 관절을 매핑한 Python 구독과 독립 ROS CLI 수신에서 재현했다.

## 확인과 증거

- `/hand_joint_controller/joint_state_command`는 `sensor_msgs/msg/JointState`이며,
  확인 당시 구독자 1개, publisher 0개였다.
- `/joint_states`의 확인된 publisher는 root namespace의
  `joint_state_broadcaster` 1개였다.
- 첫 이름 매핑 snapshot의 `right_thumb_joint1`은 `1819243124.0`,
  `right_index_joint1`은 `1309793227.0`이었다.
- 독립 확인 명령: `ros2 topic echo /joint_states --once --field position`.
- 실험 artifact:
  `data/three_model_comparison/session_20261110_01/hand_preset_inspection.json`.
- 관련 hand 코드와 하드웨어 설정은 수정하지 않았으며 에이전트는 명령을
  발행하지 않았다. 이후 운용자는 추출한 파지 각도를 한 번 발행했으나
  손이 움직이지 않았다고 보고했다.

## 파지 명령 이후 읽기 전용 점검

- 운용자의 `publishing #1` 출력은 ROS 메시지를 발행했다는 뜻이며,
  제어기의 수신·모터 실행을 확인하는 응답은 아니다.
- `/hand_joint_controller/joint_state_command` 구독자는 1개이고,
  `hand_joint_controller`, 오른손·왼손 운동학 및 actuator controller는
  모두 `active`였다. `hand_joint_controller`의 실제 `is_chained`는
  `false`이므로 chained 상태 때문에 토픽 입력이 무시된다고 단정할 근거는 없다.
- `/dynamic_joint_states`에서 오른손 encoder 15개의 position,
  status_word, error_code가 모두 `NaN`이었다. 반면 왼손 encoder 15개는
  position 약 `2937~3055`, status_word `4151`, error_code `0`이었다.
  여기서 encoder position은 원시 값이며 radian 관절 각도가 아니다.
- 오른손 joint position에도 `NaN`과 비정상적으로 큰 값이 섞여 있었다.
  모터 오류 코드 자체가 읽히지 않으므로 특정 모터 fault로 판정하지 않는다.
- 실행 중인 `robot_state_publisher`의 URDF는
  `aidin_hand_hardware/EtherlabDriver`, master `0`을 사용하고,
  왼손 slave position은 `0~4`, 오른손은 `5~9`로 지정한다.
  slave 설정 경로는 SBC workspace를 가리키는
  `/home/vision/doosan_ws/install/aidin_hand_description/share/aidin_hand_description/config/welcon_slave.yaml`이다.
  PC의 hand 소스만으로 실제 실행 바이너리의 동작을 확정하지 않는다.
- 이후 운용자는 프로그램이 SBC에서 실행 중이며 실제로는 오른손만
  연결했다고 확인했다. 양손 설정 및 오른손 시작 위치 `5`가 실제 구성과
  맞지 않는다. 오른손을 시작 위치 `0`으로 배정하고 왼손을 사용하지 않는
  실행 설정이 필요하다. 실제 slave 목록과 수정 후 동작은 아직 검증하지 않았다.
  실행 장비에서 `sudo ethercat slaves -m 0`으로 실제 구성을 확인해야 한다.
  이 조회와 별개로 enable, homing, 재시작은 실행하지 않았다.
- PC에 있는 `joint_position_controller.launch.py`에는
  `use_right_hand`, `use_left_hand`, `right_hand_position` 인자가 있다.
  `PythonExpression`에서 그대로 사용하는 boolean 인자는 `True`/`False`로
  전달한다. SBC 파일의 동일 인자 지원은 `--show-args`로 확인해야 한다.
- PC의 actuator controller 소스에는 시작 후 자동 homing timer가 있다.
  SBC 바이너리의 동일 동작 여부는 미확정이지만 재시작은 손 동작을 유발할 수
  있으므로 읽기 전용 점검의 일부로 실행하지 않는다.
- 추가 실험 artifact는 같은 session 아래의
  `hand_command_path_diagnostic.json`, `hand_drive_status_diagnostic.json`,
  `hand_raw_encoder_diagnostic.json`, `hand_running_description.xml`,
  `hand_launch_check.json`이다.
- 검증: 문서 검사 4개가 통과했다. PC의 `--show-args`는 처음에 sandbox의
  기본 ROS 로그 경로가 읽기 전용이라 실패했고, `ROS_LOG_DIR`를 `/tmp` 아래로
  지정한 뒤 통과했다. 이 실패는 SBC launch의 결함으로 해석하지 않는다.

## 조치와 재검증 기준

- 과거 `.bashrc`의 `handg` 프리셋은 확인했으나 박스 전용이라는 표기는 없다.
  원래 alias는 왼손에도 0을 명령하므로 그대로 사용하지 않는다.
- 상태 interface의 단위·매핑과 오른손 하드웨어 피드백 경로를 확인한다.
  손 제어 저장소의 변경은 별도 범위로 다룬다.
- 실제 손 자세에 맞는 유한한 radian 피드백이 Python과 ROS CLI에서 함께
  확인되고, 명령 대상과 파지 자세가 확인된 뒤 동작 검증을 진행한다.
- 같은 박스·파지 상태가 학습 조건이라는 운용자 확인을 받았다. 파지 재현 후
  그 하중 조건의 zero 품질을 확인하기 전에는 본실험을 시작하지 않는다.

## 오른손 전용 설정 후 확인

- 운용자가 설정 변경 후 보낸 ROS CLI 출력과 2026-11-10 22:36 KST의
  Python 구독에서 오른손 관절 15개의 position이 모두 유한한 radian 값으로
  확인됐다. 왼손 관절은 더 이상 발행되지 않는다.
- 현재 URDF의 encoder slave 위치는 오른손 `0~4`이며 왼손 모듈은 없다.
  오른손 관절·운동학·actuator controller는 모두 `active`다.
- 실제 dynamic joint state의 손 관절 interface는 `position` 하나다.
  `/joint_states`의 velocity·effort `NaN`은 이 관절의 제공되지 않는 필드이며,
  원시 encoder의 position·status_word·error_code가 `NaN`이던 이전 증상과 구분한다.
- 첫 추가 조회에서 `right_middle_encoder3`의 status_word `24`와
  error_code `34321`(`0x8611`), `right_thumb_encoder1`의 status_word `49`가
  관측됐다. 전자는 fault 비트가 있고 후자는 operation-enabled 상태가 아니다.
  구체적인 오류 발생·해제 원인은 확정하지 않았다.
- 후속 4회 조회에서는 오른손 encoder 15개 모두 error_code `0`이고,
  `(status_word & 0x6f) == 0x27`인 operation-enabled 상태였다.
  오류가 현재 지속된다고 판정하지 않으며 처음의 관측도 삭제하지 않는다.
- Evidence: session의 `hand_right_only_recheck.json`,
  `hand_right_only_recheck_followup.json`, `hand_right_only_description.xml`.
- 이 점검 시점에는 관절 피드백·이름 배정의 복구를 확인했고 실제 파지 동작의
  재검증이 남아 있어 상태를 `VERIFY`로 두었다.

## 파지 재검증 완료

- 운용자가 `hand_box`로 박스를 안정적으로 잡고 유지 중이며, 박스가 주변에
  닿지 않는 공중 무접촉 상태라고 확인했다.
- 후속 ROS snapshot에서 오른손 15개 관절은 유한했고 파지 목표와의 최대
  차이는 약 `0.194 deg`였다. 로봇팔은 기준 자세에서 최대 `0.355 deg` 차이이고
  관절 속도는 모두 `0 rad/s`로 읽혔다. 이는 snapshot 확인이며 장시간의
  기계적 안정성·파지력 검증은 아니다.
- Evidence: session의 `grasp_confirmation_snapshot.json`.
- 상태 `CLOSED`는 이름·slave 배정과 실제 파지 동작의 복구 확인에 한정한다.
  파지 상태의 FT zero 품질 확인은 별도로 남아 있다. 에이전트는 동작·원점복귀·
  zero-set을 실행하지 않았다.
